5. **计划模式是可选工作流，不是所有任务的强制前置条件**：
  - 用户调用 `/start-plan`，或明确要求“先写计划/基于计划讨论”时，才进入严格计划模式：计划保存在当前工作目录 `./.planning/`，讨论完成且用户明确允许后才能实施。
  - 小需求、独立 Bug、简单修改若未调用 `/start-plan`，不得强制用户先建计划文件；用户明确说“修复/实现/修改”即视为允许在完成必要排查后直接实施。若用户只是报告现象、询问原因或要求分析，不得擅自改代码。
  - 即使不使用计划模式，遇到需求矛盾、高风险数据变更、权限、安全、金额/成绩等关键计算、不可逆迁移或影响范围不清时，也必须先向用户确认关键口径。
  - 用户要求“打开计划”时，使用 `skill:plannotator-annotate ./.planning/具体计划文件.md`；若无法确定文件，先列出候选项。
  - 计划文件头部必须有描述性元信息；每次讨论或开发结束后回顾头部状态是否需要更新。
6. 使用 `skill:plannotator-*` 时，超时时间统一设置为半小时。
7. **Vue 专属规则**：
  - 要求所有新建请求函数命名以fetch开头,例如fetchCourseDetail，fetchCourseList，并且如果没给具体的后端接口 path，先返回空。
  - 请求以async/await方式，默认不处理错误，处理错误默认先提示，参考以下代码片段
    ```typescript
    const { success, content, message } = await fetchCourseList()
    if (success) {
      // 处理成功逻辑
    } else {
      // 处理失败逻辑
      Message.error(message)
      // 其他逻辑
    }
    ```
  - 不执行lint-fix，也就是不用修复 lint 错误
  - 尽量不修改原先代码，修改原先代码需要说明原因
  - 对于整页的初始请求，使用indicator，位于@/hooks 目录下，并优先使用 try-catch处理异步请求
  - components.d.ts 以及 auto-imports.d.ts文件中定义的文件，不再需要单独引入
  - 如果需要整页的表格，一般使用components/table,参考原先的代码
  - 新建vue文件的结构为，一般采用 setup 语法糖:
    ```vue
    <script setup lang="ts">
    </script>
    <template>
      <div></div>
    </template>
    <style lang="less" scoped></style>
    ```
    script 模块在前，template 模块在中间，style 模块在最后，这么做是更加方便开发，template 模块在中间能够同时与两个模块进行交互
  - 新建的样式以及 dom 结构采用 bem 命名规范命名
  - 每次引入新文件，需要检查引入是否正确，包括文件路径是否正确，文件名是否正确，文件内容是否正确
  - 遵循若无必要，勿增实体的原则
  - 公共代码谨慎修改，修改需要说明原因，且特别提示
  - 不在非error模块下使用console，error 模块错误必须处理，一般采用console.error。error 模块一般在try-catch，或者promiseInstance.catch下
8. 新增类型、枚举值、状态值必须做检索：全文检索已有字典库，位于@/store/modules/dict/index.ts switch/case，无特殊说明的字典需要统一管理。计划模式下归档到计划；非计划模式下在实现说明或最终回复中列出关键盘点结果。
9. 修一个 Bug 必须立即全文检索同模式点，避免只修一处。计划模式下登记同类点清单；非计划模式不强制创建计划文件，但仍需完成检索并在结果中简述。修复不得顺手扩大到无关模块，若同类点跨越需求边界先征求用户意见。
10. Git 权限严格受控：
   - 未经用户明确指令，禁止执行 `git add`、`git commit`；
   - 只有用户明确说“提交/commit”等才可 add/commit；
   - `git push` 一律禁止由 AI 执行；
   - 不得以保持工作区干净、自动保存进度等理由擅自改变仓库状态。
11. 实施前确认“当前有效需求”：完整阅读与当前任务相关的需求、批注和计划。新旧口径冲突时，不得自行选择看起来合理的一条；先列出冲突并让用户确认。历史结论应标记已废止，避免和当前规则同时作为实现依据。
12. 多维业务必须先建立决策矩阵，再编码：至少考虑“类型×来源”“状态×操作”“角色×权限”“有记录×无记录”“开关开启×关闭”。复杂需求在计划中形成完整表格；小 Bug 可在内部排查或回复中用轻量清单完成，不强制写长文档。
13. 业务术语必须映射到真实数据：对“有效、参与、缺勤、当前、最新、成功、已发布”等词，确认实际字段、枚举及判定条件。
14. 提测前验证规则：
   - 根据技术栈执行项目已有的格式化、静态检查、单元测试、集成测试、编译/构建；若因权限、环境或用户约束未执行，必须明确列出未验证项。
   - Vue 遵守第6条，由人工或 CI 编译；AI不得宣称编译通过。
   - 计划模式下把验证项写入对应步骤；非计划模式采用与改动规模相称的轻量验证，不强制建立计划。
