# 进入计划模式（/plan-start）

本次需求补充信息（可为空）：$ARGUMENTS

> 本命令是新版分片计划模式，与旧版单文件模式 `/plan-start-old` 并存；旧版保持不变。

## 〇、启用判定

先判断本任务是否适合计划模式：

- 适合：多步骤且需分批验收；跨模块或多人协作；预期跨度超过一天。
- 不适合：孤立 Bug、单点修改、一句话能说清的小需求——直接按全局准则实施，不建计划。
- 拿不准：先不开；实施中复杂度上升时，可随时重新调用本命令从半路建计划（协议不强制从头开始）。

若判定不适合，直接告知用户理由并退出本流程，不得强行建计划。

## 一、激活与状态

1. 计划模式状态落盘于 `./.planning/active.json`：
   `{"mode":"active","需求":"<需求目录名>","当前步骤":"S01","文档版本":1,"最近变更":[],"更新时间":"..."}`。
   **文档版本**用于标识计划源文件被 AI 修改的次数，每次 AI 真正写回计划内容（index/steps/anchors）时自增 1；单纯重新构建 html 不增加版本。
2. 进入时：active.json 不存在或 mode=off → 进入新建/恢复流程；mode=active → 询问用户恢复当前需求、切换其他需求目录还是新建。
3. **计划模式下每轮回复前，必须先读 active.json 与当前需求的 index.md（均为小文件，禁止全文读步骤片段）**，并在回复首行声明：`📋 计划模式 · <需求> · 当前步骤 Sxx · 未决讨论点 N 个`。这是多窗口并行工作时的模式标识。
4. `/plan-off` 或计划完成后：active.json 的 mode 改为 `off`（文件保留），此后行为与非计划会话一致。
5. 计划模式激活后执行 `node ~/.pi/agent/bin/plan-mode.mjs install`，将核心规则同步到当前项目 `AGENTS.md` 的受管控区块；不得改写该文件的其他内容。同步完成后提醒用户执行一次 `/reload`，使当前会话重新加载项目级 context files。

## 二、核心约束

1. 先完整阅读需求文档、原型、附件、项目约束及相关代码，再编写计划；不得改写需求文档原文。若需求文档包含责任人、角色、任务分配或明确不负责项，必须先提取，不能把整份需求默认当成当前用户的实施范围。
2. 计划讨论阶段只能阅读、检索、只读数据侦察和修改计划文件；禁止修改业务代码或执行破坏性命令。
3. 只有用户明确表示"按计划实施""开始开发""可以修改"等，才能编码；默认只实施明确授权且状态为 🟢 的步骤。进入实施前，当前步骤的普通待讨论点、`待讨论接口设计`和`待讨论代码设计`必须全部确认；历史已完成步骤按新旧兼容规则处理。
4. 所有疑问、反馈、口径确认和方案取舍必须写入对应步骤片段的"待讨论点"；未写回计划文件的对话结论不视为共识。
5. **每次写回计划文件后必须完成三个同步动作**：
   - 写回所有受影响计划片段（index.md / steps / anchors.md）；
   - 更新 active.json：`文档版本` +1，`当前步骤`、`最近变更`、`更新时间`同步修正；
   - 执行 `/plan-build`（底层为 `node ~/.pi/agent/bin/plan-build.mjs ./.planning/<需求>`）重建 html；用户使用浏览器原生刷新查看最新构建结果，最近变更的讨论点会高亮。

## 三、协作范围与责任边界

`/plan-start` 初版规划前必须先做一次轻量责任矩阵，避免把协作方的工作误写成当前用户的任务：

1. **读取三类依据**：
   - 需求文档中的责任人、角色、任务分配、交付物和明确不负责项；
   - 先执行 Agent Forum 的 `context resolve --json`。若当前工作区绑定活跃 Room，再执行一次 `inbox`，读取已确认分工、决策、依赖、阻塞和相关 proposal；未绑定时不创建论坛、不臆测存在协作消息；
   - 当前对话和项目约束中对当前用户的显式授权。
2. **按责任归类**：
   - 明确由当前用户/当前角色负责：标记为`我负责`，进入自己的 Sxx 执行步骤；
   - 明确由他人负责：不拆成当前用户的实施步骤，登记为`外部依赖`，记录责任方、对方交付物、影响的我的步骤、需要确认的事项和当前状态；
   - 我的工作必须等待他人契约、决策、接口：保留为我的协作步骤，但把等待内容单独列为外部依赖，并建立对应讨论点或协作问题；
   - 共同负责、责任人不明、需求文档与论坛冲突：初版标记`待确认`，只有会改变任务边界时才向用户提出一个高层确认问题，不因细节未定阻塞总体骨架。
3. **初版计划只规划我的工作**：他人的工作可以作为依赖、输入、里程碑和讨论项出现，但不得伪装成我将实施的步骤，也不提前替协作方展开其内部实现计划。
4. **计划文件必须显式区分**：index.md 元信息增加`我的任务范围`、`外部依赖`、`不纳入本次范围`；每个步骤增加`责任与协作`小节，写明责任归属、依赖方、我需要的输入和阻塞条件。外部依赖需引用论坛 Thread/Message（如有），没有则写`暂无论坛记录`。
5. 初版总体规划阶段只确认责任边界和主要依赖，不批量追问接口字段、异常分支等细节；这些内容按零售式讨论在后续每轮只展开 1~3 个相关点。责任明确时直接形成骨架，只有责任边界不明才提问。
6. 论坛中的 proposal 不等于已确认分工；需求文档、已确认 Forum decision 与当前用户明确结论出现冲突时，不得自行择一，先登记冲突并向用户或责任方确认。协作消息如果改变责任边界、依赖状态或实施顺序，必须同步回 index/步骤片段。

## 四、文件协议

```text
./.planning/
├── active.json              # 模式状态（项目级）
└── <需求短名>/
    ├── index.md             # AI 每轮入口：元信息 + 步骤总表 + 未决速览（≤100 行）
    ├── anchors.md           # 需求原文锚点（A-01 起，讨论点引用，不集中抄原文）
    ├── steps/
    │   ├── S01-xxx.md       # 每步一个片段，固定栏目自包含
    │   └── ...
    ├── review/              # 每批完成时：Sxx-Bxx-review.md
    └── build/plan.html      # 生成物，人看视图（勿手改，由构建脚本生成）
```

- 需求短名：取稳定的需求标题，空白转短横线，去非法字符；同需求已有目录则更新，有多个候选目录时先让用户选择。
- 需求资料（PDF/原型/附件）可放 `./.planning/` 下，但不得被计划文件覆盖。

## 五、index.md 规范（AI 每轮唯一入口）

1. **元信息表**：计划名称、需求来源、计划状态（`规划中`/`实施中`/`阻塞`/`待验收`/`已完成`/`已取消`）、当前重点步骤、有效需求版本、我的任务范围、外部依赖、不纳入本次范围、最后更新时间。
2. **步骤总表**（步骤顺序的唯一权威来源，表头固定不得改）：
   `| 步骤 | 名称 | 状态 | 文件 | 内容 |`（文件列写相对路径如 `steps/S01-xxx.md`，内容列一句话）。
3. **未决讨论点速览**：仅列未决项（待讨论/讨论中）：`| 编号 | 所属步骤 | 疑问 |`，写回时同步维护；全量讨论点聚合表由构建脚本自动生成，不在此重复维护。
4. 总长控制在约 100 行以内，细节一律放片段文件；超出时先精简再追加。

## 六、anchors.md 规范

1. 建计划初版时一次性从需求文档提取关键原文：`| 锚点 | 需求章节 | 原文摘录（≤2 句） | 备注 |`，编号 A-01 起、不复用。
2. 步骤"关联需求"与讨论点一律引用锚点（如 `[A-03]`），不在多处重复抄原文。
3. 需求版本更新时：新增锚点或将旧锚点备注标"已废止"，不得改写历史锚点原文。

## 七、步骤片段规范（steps/Sxx-名称.md）

固定结构：

```markdown
# S01：🟦 步骤名称
## 关联需求
## 现状
## 内容
## 实施批次
## 责任与协作
## 待讨论点
### 待讨论代码设计
## 产出
```

### 待讨论代码设计

每个新步骤必须在`待讨论点`下增加此子项；历史已完成步骤无需追溯迁移。只要新增、删除、拆分、合并页面/组件/composable（`@/hooks`）/store/请求函数（`fetch` 开头），或修改组件 Props/Emits、状态流向、依赖、调用链、响应式状态、生命周期、异步请求与副作用，就必须逐项讨论相关页面/组件/函数；无结构变化时明确写“本步骤无代码结构变更”。

建议表头：

`| 编号 | 类型 | 页面/组件/函数 | 职责 | 调用方/时机 | Props/参数/返回值 | 内部流程 | 状态/副作用/边界 | 复用判断 | 状态 | 结论/影响 |`

AI 必须围绕每个关键页面/组件/函数逐轮提出 1～3 个问题，要求用户用自己的话说明：为什么存在、何时渲染/调用、Props/参数从哪里来、返回值/渲染结果代表什么、内部做什么、异常/空值/重复提交/竞态如何处理、为什么复用或不复用已有组件。用户未能说明关键链路时，状态不得改为`已确认`。

### 批次 Review 的代码结构与调用清单

批次 Review 使用`## 代码结构与调用清单`标题，记录实际涉及的页面/组件/composable（`@/hooks`）/store/请求函数（`fetch` 开头）的职责、调用入口与时机、Props/参数/返回值、内部流程、状态/副作用/边界、复用边界和设计与实际差异。无结构变化时明确写“本批次无代码结构变更”。这份清单用于个人理解，不单独生成对外使用手册。

建议表头：

`| 类型 | 页面/组件/函数 | 实际职责 | 调用入口/时机 | Props/参数/返回值 | 内部流程 | 状态/副作用/边界 | 复用边界 | 设计与实际差异 |`

1. 步骤 ID（S01、S02…）稳定且不复用，**ID 不表达顺序**（顺序由 index.md 步骤总表决定）；拆分产生的新步骤取下一可用 ID。
2. 状态图标：🟦 待讨论、💬 讨论中、⛔ 阻塞、🟢 可实施、🚧 实施中、✅ 已完成；状态变化时同步更新片段标题与 index.md。
3. **步骤必须自包含**：执行与审阅本步骤所需的页面/数据结构、关键字段、枚举值、状态含义、接口契约和决策规则直接写在本步骤；禁止只写"见上文/见第 X 章"。
4. **实施批次**必须在首次编码前声明：使用 B01、B02…稳定编号，写明每批范围、前置依赖、预计产出、验收条件和状态（`待实施`/`实施中`/`已完成`/`阻塞`）。如果初版无法拆细，必须在开始编码前补齐，不得让批次只存在于对话或 active.json 最近变更中。
5. **责任与协作**必须明确写出：`责任：我负责/协作依赖/待确认`、责任方、外部输入、阻塞条件；他人负责的实施内容只写协作边界和验收输入，不展开为当前用户的开发任务。
6. **待讨论点表格**（构建脚本按表头解析，列名固定不得改）：
   `| 编号 | 锚点 | 事项 | 方案选项（→推荐） | 状态 | 结论/影响 |`
   - 编号 T-01 起全局唯一、永不复用（跨全部步骤与演化）；
   - 普通讨论点状态：`待讨论`/`讨论中`/`已确定`/`搁置`/`已废止`/`已下分`；代码设计点状态：`待确认`/`已确认`/`不适用`/`已下分`/`已废止`；
   - 结论确定后必须同步改写本步骤正文及受影响的其他步骤，不能让旧口径并列生效；
   - 下分规则：归属其他步骤的项登记"已下分至 Sxx"并写入目标步骤待讨论点，不再阻塞本步骤收尾。
7. 历史兼容：历史已完成步骤可以保留旧 Review；不因缺少新代码设计或新 Review 清单而阻断。新步骤以及历史步骤新增批次必须使用`待讨论代码设计`和`代码结构与调用清单`。

## 八、演化规则（开放调整 + 全局掌控）

1. **初版必须一次性列出全部步骤骨架**：后续步骤可先简写，但固定栏目齐全；用户据此掌控全局。
2. 计划必然演化，允许四类操作：
   - **顺序调整**：只改 index.md 步骤总表顺序，不动文件；
   - **拆分**：新建下一可用 ID 的片段文件，原步骤对应栏目登记"已拆出至 Sxx"；
   - **合并**：内容并入保留文件，T 编号随迁，删除冗余文件并更新 index.md；
   - **阻塞部分后挪**：阻塞内容移入新步骤片段，原处登记"已挪出至 Sxx"。
3. 每次演化后必须自检：grep 全部步骤 ID 与 T 编号引用，确认无悬空引用；同步 index.md 与 active.json。
4. 讨论前序步骤时顺带确定的后续步骤内容，直接写回对应后续片段，不等"轮到它"。

## 九、讨论规则（零售式）

1. **每轮最多抛 1~3 个相互关联的待讨论点**，每个点必须在对话中给出：锚点对应的需求原文（从 anchors.md 带入对话）、疑问、方案选项与推荐及理由；禁止一次性批发全部讨论点要求拍板。
2. 用户可按顺序或跨步骤讨论；每轮结束完成"三同步"（第二节第 5 条）。
3. 初版完成后只汇报：计划路径、步骤总表、未决讨论点速览、建议先讨论的 1~3 个点及理由，然后停止等待，不得直接编码。

## 十、实施与写回

1. 获得授权后只开发本轮明确授权且标记为`我负责`的步骤；不得因为需求文档列出了协作方任务，就越权代替协作方实施。
2. 外部依赖未完成时，只能实施不依赖该输入的部分；对确实阻塞的部分登记阻塞原因、责任方、所需输入和下一次跟进，不用猜测方案替代协作确认。
3. 协作确认可来自当前用户、需求文档的明确更新或 Agent Forum 已确认消息；proposal、未回复问题和推测不视为完成确认。
4. **批次开始时**：将对应 Bxx 状态改为`实施中`，将所属步骤状态从`🟢 可实施`改为`🚧 实施中`，同步 index.md 与 active.json。
5. **每个批次完成时必须执行批次收尾，不得等待整个 Sxx 完成**：
   - 将 Bxx 改为`已完成`，所属 Sxx 保持`🚧 实施中`；
   - 写回步骤片段“产出”：本批次修改、验证结果、未验证项、提交版本或“未提交”；
   - 同步 index.md、步骤片段、active.json，文档版本 +1；
   - 建立 `review/Sxx-Bxx-review.md`；
   - `Sxx-Bxx-review.md` 必须按“图先于文”组织：先放一张 `页面与组件脉络图`（使用 mermaid flowchart，展示本批次涉及的页面结构、组件层级与数据/事件流向，主干不超过 15 个节点），再放需求意图与锚点、修改文件总览、关键风险、自测结果、未验证项、建议 Review 顺序；关键节点可用 Mermaid `click` 指向对应 Review 细节。
   - `## 代码结构与调用清单`必须反映实际实现，记录页面/组件/composable（`@/hooks`）/store/请求函数的职责、调用入口与时机、Props/参数/返回值、内部流程、状态/副作用/边界及设计与实际差异；无结构变化时明确写“本批次无代码结构变更”。
   - 完成批次前执行`理解验收`：AI 每轮只问 1～3 个关键问题，用户用自己的话复述需求→接口→页面/组件/函数→数据/状态副作用→测试链路；关键误解未消除时批次不得标记为已完成。
   - 执行 `/plan-build`，向用户交付挂在对应 Sxx 下的 Review 入口，允许用户先看图、代码理解清单，再进入文件细节。
6. **步骤完成门禁**：只有所有 Bxx 批次完成、外部依赖已对齐、步骤级验证完成并通过用户验收后，Sxx 才能改为`✅ 已完成`；批次完成不得直接将步骤标记为完成。
7. 若批次部分完成但仍需继续，状态必须为`🚧 实施中`，不能继续保留`🟦 待讨论`或伪报`✅ 已完成`。
8. 最后一个步骤完成后：汇总未验证项、人工/CI 待办、提交与迁移版本、已知限制；完整业务闭环验收后计划标记“已完成”，执行 /plan-off 退出计划模式。

## 十一、Bug 记录

仅记录功能上线后用于复盘的 Bug，写于 index.md 尾部（或独立 bug-log.md），按 `Bug-001` 递增；每项至少记录版本、现象、影响、根因、修复、同模式排查、验证、预防措施、关联步骤和状态；初版写"暂无上线后 Bug"。
